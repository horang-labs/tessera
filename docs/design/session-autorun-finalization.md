# Autorun finalization and analysis recovery (#529 clarification)

Status: **design clarification, not implementation certification**. Review base: `f9989c3db0d48dd61f79b8e9e34346418e831e07`. This resolves [#529's reopened finalization question](https://github.com/horang-labs/tessera/issues/529#issuecomment-5958527069) from #533's actual independent Spec review. It narrows ambiguous wording in the [architecture](session-autorun-architecture.md) and the [frozen contract note](session-autorun-contracts.md); it does not edit public types, change the [UX readiness rules](session-automation-ux.md#6-takeover-edits-and-resume), or certify live siblings.

## Decision: fresh native observation, then atomic host admission

**Keep the asynchronous bounded native re-read followed immediately by synchronous runtime checks and DB CAS. Do not add a synchronous filesystem verifier inside the gate.** The prefix check is a comparison against newly observed captured bytes, not merely the cached pre-model snapshot. The synchronous gate makes Tessera's runtime checks and conditional persistence indivisible with respect to its own interleaving state transitions; it does not lock a provider-owned file or create a filesystem/SQLite transaction.

The disputed architecture sentence “A read-then-write check outside the gate is insufficient” applies to **runtime/input identity and DB eligibility**. Those must still be checked together inside the gate for `continue`, `complete` and `needs-user`. The contract comment “check runtime identity and snapshotted prefix” means compare the fresh provider capture's attestation to the saved analysis identity there. It does not require filesystem I/O while holding the gate.

Reasoning: provider files are written by a separate CLI, potentially across Windows/WSL. A `readSync` followed by a DB commit still leaves the external writer free to modify bytes after that read; a multi-read 32 MiB scan is not an atomic snapshot either. Moving it inside the gate adds blocking I/O without the claimed exclusion. Node documents that synchronous filesystem calls block the event loop, and that filesystem promise operations are not synchronized. The absence of an external-writer lock follows from this process boundary, not from an assertion that async reads are atomic. [Node filesystem reference](https://nodejs.org/api/fs.html#synchronous-api), [promise operations](https://nodejs.org/api/fs.html#promises-api).

The exact proof claim is **“captured native content re-observed after model completion; current Tessera identity/eligibility checked at atomic host commit.”** It is not “the entire transcript was immutable at DB commit.” Detect persistent mutations visible in the compared bytes, replacement/truncation/binding changes and all relevant state changes visible to the gate/CAS. An arbitrary external mutation after its bytes were observed, a rewrite-and-restore between observations, or a native event not yet delivered to Tessera is outside a linearizability guarantee. Neither switching to sync reads nor a file watcher closes those windows. This explicitly qualifies the old unimplementable reading of “prefix unchanged at commit”; it does not permit accepting a mismatch actually observed. No cooperative provider lock, new scheduler, or generic transaction framework is introduced.

## What exactly is compared

R1's `readAnalysisContext` remains the provider-owned capture seam. R2 consumes the snapshot and never opens the provider path itself. Existing owner/environment resolution, canonical CLI-side path, provider conversation, file generation, correlated completed-turn cutoff and latest-turn coverage checks remain mandatory.

- `contentHash` attests the **exact native bytes in the captured ranges through the frozen cutoff**, including human records and raw tool bytes scanned but omitted/truncated in the model packet. No whitespace normalization or assistant/tool-only digest. R2's separate normalized `evidenceHash` is only for no-progress detection.
- Compare stable source identity/generation, cutoff identity/end byte, latest-turn start, parser/provider binding, and the ordered **captured range coordinates plus their bytes digest**. Pairing coordinates with the digest prevents different disjoint ranges with identical concatenated text from masquerading as the same capture. This need not add a DTO: project the existing `scannedRanges` onto the attested ranges at/before the frozen cutoff, alongside existing snapshot identity fields. Earlier unscanned gaps remain explicitly omitted, not certified unchanged.
- Freeze that capture plan for revalidation, or use an equivalent deterministic plan derived from the same native correlation/cutoff. File growth must not move the old-history window, change the captured range set, or switch policies merely by crossing a size threshold. Do not deep-compare incidental `bytesScanned`, read retries, post-cutoff scan accounting, capture timestamps or whole-file size/mtime. Such metadata may help detect instability during one read; it is not cross-read content identity.
- A complete harmless bookkeeping append **strictly after** the cutoff leaves the attested ranges, bytes and identity unchanged and must pass. New worker/child work is not classified as harmless bookkeeping: the runtime/binding/boundary checks still reject observed work. Replacement, changed generation, truncated coverage, same-length user/tool edits, or a changed/missing correlated final record must fail. Do not use matching size/mtime as a substitute for reading the bytes.
- Within a capture, validate the opened source identity and binding before/after the read; reject observed replacement, shrink, malformed/partial required records or ambiguous latest-turn lineage. Hash the bytes actually parsed, not a separately reread sample. Ordinary append-only completed histories remain the supported model; a stat pair cannot certify absence of an adversarial concurrent rewrite. Avoid unbounded retry-until-stable loops.

Each capture retains the frozen **32 MiB actual-read budget, including retries**, 2 MiB record ceiling, bounded packet, complete latest turn and explicit omission accounting. A transcript larger than 32 MiB does not require reading the entire file. The producer must make the stable-range/harmless-append pair pass within those limits; inability to do so is unavailable, not permission to omit required latest bytes or to silently drop integrity checks.

## Finalization sequence and latency

1. Before launching a model, persist the immutable packet, captured identity/digest, selected supervisor, decision/attempt identity, deadline and budget reservation. Existing boundary ledger and revision semantics remain unchanged.
2. After a strictly valid model final result and verified owned-process quiescence, finish unrelated asynchronous prerequisites **before** the final provider capture. R2 requests the same qualified boundary/correlation; R1 returns a fresh bounded observation. Cache-only equality against the pre-model packet is insufficient.
3. R2 compares that observation with the saved identity, then in the **same uninterrupted synchronous continuation after the capture facade returns**, invokes `commitAnalysisDecision` and its synchronous DB CAS. No intervening await, timer, queue, notification, provider call or reuse on a later attempt. A necessary subsequent async prerequisite invalidates this handoff: repeat the final capture before attempting commit. Provider-side close/binding checks are part of the bounded capture facade, not a hidden file lock.
4. Under the gate, recheck expected runtime/server/generation, owner/environment, input epoch/revision, boundary/turn/binding, child/approval safety and exact saved worker selection, plus the fresh captured identity. The DB CAS rechecks decision/attempt eligibility, rule enabled/revision, goal revision, selected supervisor, lease, expiry and analysis deadline. Rejection or throwing leaves no current outcome/run/attention published. Consume/discard the local fresh-capture evidence after the attempt; do not let a later call reuse it to bypass step 2. This can be private R2 call-path state, not a new public provider capability.
5. Only after successful commit may publication happen. `continue` still creates one immutable linked run and uses the existing final writer fence; neither content verification nor a decision grants a write permit. `complete`/`needs-user` retain zero worker writes. Pause/selection/boundary changes before dispatch still invalidate delivery.

Keep the final capture outside the synchronous gate and DB transaction. Its logical admission timeout is **at most the existing 10-second context-read allowance, further capped by remaining analysis deadline and rule expiry**; do not restart/extend the analysis deadline after model return. R2 must reject/ignore a late capture and abort owned read work where supported, including when native I/O does not settle promptly. Cancellation of a promise is not proof that an OS read stopped: retain bounded outstanding read ownership and cleanup, never launch unbounded replacements or let a late callback commit. The byte cap alone is not a latency bound, especially over a WSL path. The gate contains only bounded in-memory checks and synchronous conditional persistence, not transcript scanning.

Read-only observation of live siblings at the start of this clarification: R1 HEAD `dfd700d0` plus uncommitted context changes hashes raw native bytes; R2 HEAD `16692109` plus uncommitted fixes re-captures after the model and immediately gates the returned result. R2's `captureAnalysisContext` wrapper additionally awaits saved-selection loading **after** R1's read; move optional async selection work before the final native capture and keep the final synchronous selection check, rather than describing the raw read-to-commit interval as await-free. Its current source comparator also omits captured range coordinates; the requirement above covers that gap without a new synchronous-file port. These are actionable observations, not a full sibling review or a claim that their moving working trees are final.

## Analysis uncertainty and worker input are separate holds

| Situation | Required input and analysis behavior |
| --- | --- |
| Pause/Delete/expiry or cancellation while only analysis exists | Persist inhibition and invalidate decision generation first. With no worker writer or unknown prior write, ordinary drain returns human ownership for the live runtime even if isolated supervisor exit is uncertain. Keep the invocation quarantined and consuming its analysis capacity. A late result cannot commit, announce completion or acquire a writer permit. |
| Actual worker paste/Enter started, or prior worker write outcome unknown | Preserve the existing 202/drain/recovery-required hold until writer quiescence/recovery. A supervisor settlement receipt cannot release this hold or acknowledge delivery. |
| Backend restart after analysis intent, with no writer intent | Mark the decision interrupted/cancel unsent work, retain uncertain invocation and analysis-slot accounting. Reconcile actual worker ownership through existing runtime recovery; lack of supervisor settlement alone must not deny otherwise safe manual input. Never execute a cached proposal or rerun that boundary. |
| Exact owned invocation later proven quiescent | Release only that invocation's analysis quarantine/capacity idempotently. Keep the rule inhibited (paused/deleted/expired as applicable) and counts/consumed boundaries unchanged. Explicit fresh-boundary re-arm is a separate operation. |

Thus an analysis-only `recovery-required` input lock is not the solution. User text remains possible after safe worker drain while UI can truthfully say automatic analysis is unavailable pending settlement. Do not downgrade actual write uncertainty because the current attempt happened to be analysis-only; check the worker's unresolved writer history as well.

## Minimal settlement capability and ownership

The parent-authorized **owner/environment/invocationId-scoped settlement observation** is sufficient for restart recovery **if it has these semantics**. No second cancellation API or synchronous prefix API is needed. R1/#532 alone owns the optional versioned provider method/result, its exact exports in `src/lib/cli/providers/session-types.ts` (and a result DTO only if needed), provider-side implementation/fixtures and handoff in `session-autorun-contracts.md`. R2/#533 consumes those agreed exports and owns persistence, accounting/admission and worker drain. #529 changes no public contract or sibling file.

- Before a process can launch, R1 durably binds the unique invocation to owner, agent environment, provider and owned execution identity on the **CLI filesystem**, with enough information to resolve it after backend restart. R2 already durably reserves that invocation ID before calling R1. A backend-local map alone is insufficient. Resolve through existing bridged path helpers and validate the association; never accept a caller-supplied path/PID as ownership.
- Observation is bounded, read-only with respect to execution: it returns verified **quiescent**, positively **running**, or **unknown/unavailable** evidence for that exact invocation. No inference, new model call, output replay, auto-rearm or blind process kill. Absence of a receipt, absence of a PID, or PID reuse cannot be interpreted as successful settlement.
- Quiescent evidence proves **launch is terminal (no delayed launch remains possible)** and all processes within the proven owned invocation scope have settled, not merely that the parent/wsl.exe exited or an instant process scan was empty. Match durable invocation identity and process birth/generation information, reject stale/cross-owner receipts, and retain evidence until R2's durable settlement update can survive another restart. The exact receipt/index/cleanup implementation stays with R1; no global scanner of unrelated Sessions is authorized.
- R2 can request observation on recovery/re-arm and bounded reconciliation ticks. Persist the result by exact invocation/attempt before releasing its slot; handle duplicate observations and crashes around that write idempotently. A timeout/error/missing method means unknown, keeps quarantine and does not re-lock safely returned human input. Late supervisor output remains invalid even after its process settles.
- Autorun re-arm requires **all unresolved analysis invocations relevant to that Session's continuation admission** to be proven settled, including an old paused/deleted rule after method replacement; keep their slots in the profile concurrency count. Do not bypass quarantine by creating a new Autorun rule. Unrelated Sessions may use remaining proven capacity. After settlement, recheck normal capability, budget/expiry, owner/environment/selection and a newly accepted instrumented running turn or fresh eligible completed boundary. Consumed idle retains human input and the “send a new instruction first” path.

This closes the recoverable case “host lost the cancellation handle, but the owned invocation later has durable settlement evidence.” It does **not** promise automatic recovery when that proof is permanently missing or ambiguous; keep Autorun unavailable while manual work remains possible. R1 must prove restart lookup and evidence retention, and R2 must prove release plus fresh-boundary re-arm—not just define the method. The inspected R1 port had not yet exposed this amendment; ongoing producer/consumer work must be reviewed on its final commit.
